## System and repository

```text
React Native app (Expo, Expo Router)
  → Clerk session and token
  → shared API client and TanStack Query
  → NestJS REST API
  → verified identity, validation, and ownership checks
  → Prisma → PostgreSQL
```

The pnpm workspace contains `apps/mobile` and `apps/api`, with repository guidance in `docs`. Both starters use TypeScript. Add shared packages such as `packages/types` or `packages/config` only when real reuse exists. GitHub Actions checks live under `.github/workflows`; the initial CI workflow checks API quality and tests plus mobile TypeScript.

## Mobile responsibilities

Expo Router owns navigation. The root `_layout.tsx` mounts Clerk and a root Stack. `sign-in.tsx` is public; the `(app)` group contains Home and Explore and its NativeTabs layout, protected by `Stack.Protected` after Clerk finishes loading. This client-side route gate improves navigation behavior but does not replace API authorization. The screen separates password sign-in from account creation. Sign-in calls `signIn.password({ emailAddress, password })` and finalizes complete attempts. When Clerk reports `needs_client_trust` or `needs_second_factor`, the helper checks supported factors and can send and verify an email code. Account creation calls `signUp.password({ emailAddress, password })`, sends an email verification code when `email_address` is unverified, verifies it, and finalizes the sign-up attempt. If Clerk still requires a supported profile field, the screen collects first name, last name, or username and updates the attempt before finalizing it. These decisions live in pure helpers with Node specs. Sign-in errors remain generic to reduce account enumeration; sign-up displays only Clerk's designated user-facing `longMessage`, never raw developer details. Unsupported verification or profile requirements allow a restart. Keep both password sign-in and password sign-up enabled in Clerk Dashboard. New account verification uses email codes. Clerk settings and real sign-in/sign-up remain to be verified against the Development instance. Later routes include a tab layout for calendar, writing, memories, and profile, plus entry detail and edit screens. Route files should stay focused on screens; feature components and hooks handle presentation and behavior. A feature hook calls an API function, which uses a shared API client to set the base URL, attach a Clerk token in the authorization header, and normalize errors. TanStack Query owns remote server state, query keys, mutations, and cache invalidation; use optimistic updates only when their failure behavior is clear. React Hook Form and Zod are available when they simplify forms and validation. Zustand is reserved for genuine shared client state, such as an unsaved draft, and must not duplicate the server cache.

Use NativeWind for app-owned mobile UI styling across iOS, Android, and web. Prefer NativeWind utility classes for new and updated screens and components; use `StyleSheet` or platform-specific styling only when required by a native API or platform behavior. NativeWind 4.2.7 and Tailwind CSS 3 are installed, and `apps/mobile/tailwind.config.js` scans `src` and enables the NativeWind preset. The existing `src/global.css` includes Tailwind's base, components, and utilities directives while preserving the app's font variables. `apps/mobile/babel.config.js` applies the Expo and NativeWind Babel presets. `apps/mobile/metro.config.js` wraps Expo's default config and points NativeWind at `src/global.css`. Expo web uses the Metro bundler, and the root layout is the sole importer of the global CSS. ## API responsibilities

Keep each module, controller, and service focused on one responsibility.

NestJS is planned with feature modules for authentication, users, entries, tags, Prisma, and health, plus common cross-cutting code. Dependency injection keeps responsibilities clear. Controllers receive HTTP input through explicit validated DTOs, obtain the authenticated identity, delegate to services, and return responses. Candidate DTOs include `CreateEntryDto`, `UpdateEntryDto`, `EntryQueryDto`, `CalendarQueryDto`, and `CreateTagDto`. Services apply application rules and ownership-aware data access through one `PrismaService`; do not instantiate Prisma clients throughout feature modules. Controllers must not query Prisma directly, repeat token parsing, contain business rules, or accept Prisma input types as public request contracts. Avoid repository wrappers that add no value.

The initial REST entry contract is planned around `POST /entries`, `GET /entries`, `GET /entries/:id`, `PATCH /entries/:id`, `DELETE /entries/:id`, `GET /entries/date/:date`, and `GET /entries/calendar`. `POST /entries` is implemented; the other routes remain planned. `GET /entries` will eventually accept validated `page`, `limit`, `search`, `mood`, `favorite`, `tag`, `dateFrom`, `dateTo`, `sortBy`, and `sortOrder` parameters. Swagger/OpenAPI is not configured yet.

The first create-entry slice is a protected `POST /entries`. The request has required nonblank `content`, a required real calendar date in `YYYY-MM-DD` form as `entryDate`, and an optional `title`; it does not accept `userId`. The route binds `CreateEntryDto`, and NestJS `ValidationPipe` uses `whitelist` and `forbidNonWhitelisted` so unexpected properties, including `userId`, are rejected. Keep transformation disabled unless a specific field needs it; check that `content` contains non-whitespace without silently changing the value that gets stored. The DTO reuses the standalone `isValidEntryDate` helper through a custom validator. The controller requires the verified Clerk identity and passes that ID to `EntriesService`; the service creates an owner-linked Prisma record and returns an `EntryResponseDto`. A successful response is HTTP 201 with an opaque `id`, saved `content`, `title` or `null`, unchanged `entryDate`, and `createdAt` and `updatedAt` timestamps. Invalid input is rejected with HTTP 400, and missing or invalid authentication with HTTP 401. E2E tests currently verify missing and malformed authentication, while DTO validation is tested at pipe level; database persistence and owner behavior are covered by a passing PostgreSQL integration test; a successful authenticated HTTP creation remains unverified. See [NestJS validation](https://docs.nestjs.com/techniques/validation).

## Authentication and authorization

Clerk owns sign-up, sign-in, sign-out, email verification, sessions, and tokens; OAuth can be added later if needed. `main.ts` registers `clerkMiddleware()` in the Express request pipeline. `ClerkAuthGuard` uses Clerk's `getAuth()` and requires both `isAuthenticated` and a user ID. `AuthController` applies that guard to `GET /auth/me` and returns `{ userId }` from the verified request state. `EntriesController` applies the guard to `POST /entries` and takes the owner ID only from verified request state. The middleware provides authentication state but does not protect a route by itself. Never decode a token without verifying it. The starter `GET /` remains public. The HTTP tests verify `/auth/me` and `/entries` reject missing and malformed bearer credentials. `main.ts` also configures CORS for the local Expo web origin (default `http://localhost:8081`, configurable through `EXPO_WEB_ORIGIN`), allows `GET`, `POST`, and preflight with the `Authorization` header, and does not grant an unconfigured origin access. All 3 CORS e2e tests passed, including the POST preflight. The signed-in Home retrieves a token with Clerk's `getToken()` and calls the API through `fetchCurrentUser`; its 7 unit tests pass, and the user confirmed a real signed-in Expo web request displayed `API session verified`. A successful authenticated `POST /entries` is not yet verified. Configure Clerk's `authorizedParties` from the actual web origins when known; do not use a broad allowlist by default. NestJS will not duplicate Clerk's login endpoints.

Every entry and tag belongs to a user. The API must scope reads, lists, updates, deletes, search, and calendar results to the authenticated owner and prevent cross-user tag attachment. A client-provided `userId` never establishes ownership.

## Data model and dates

The planned local `User` has `id`, a unique Clerk ID, optional application-specific `displayName`, `createdAt`, and `updatedAt`. Clerk owns identity while Tinta owns application data and relationships. `DiaryEntry` has `id`, `userId`, `title`, `content`, `entryDate`, `mood`, `isFavorite`, `isPrivate`, `createdAt`, and `updatedAt`. Planned moods are `HAPPY`, `EXCITED`, `CALM`, `NEUTRAL`, `SAD`, `STRESSED`, `ANGRY`, and `TIRED`. `Tag` has `id`, `userId`, `name`, `createdAt`, and `updatedAt`; an entry-tag relation connects `entryId` and `tagId`. The API must prevent a user's entry from attaching another user's tag.

The initial Prisma schema now defines `User` with a unique `clerkUserId` and `DiaryEntry` with required `userId`, `content`, and `entryDate`; `title` is nullable. A non-unique `(userId, entryDate)` index supports future owner-scoped date queries, and the required user relation has restrictive deletion in the previewed SQL. Mood, favorites, privacy flags, and tags remain planned and are absent from this first schema. Prisma validation and client generation passed. The reviewed initial migration was applied to the empty local development database. `EntriesService` creates an entry with a nested `connectOrCreate` for the local user keyed by the verified Clerk ID; it maps dates and explicitly selects the agreed response fields. The response contract is an `EntryResponseDto` class with `@Exclude` and `@Expose` markers, instantiated through `plainToInstance` with `excludeExtraneousValues` so internal Prisma fields are omitted. Four mocked-client unit tests passed, and the service is now attached to the protected `POST /entries` route. A real PostgreSQL integration test verified persisted content, nullable title, date-only values, multiple same-day entries, and separate owner links. The generated client lives in an ignored directory and CI is configured to regenerate it before API type checks; that CI change has not yet run in GitHub Actions.

`entryDate` is the user's intended calendar day, represented at the API boundary as `YYYY-MM-DD`. The mobile app defaults to the user's local today but sends the selected day explicitly; changing time zones must not move an entry to another diary day. Multiple entries may share a day, so `(userId, entryDate)` must not be unique. `createdAt` and `updatedAt` are event timestamps. Store `entryDate` as PostgreSQL's native `date`, not a timestamp. The Prisma ORM v7 schema maps it with `DateTime @db.Date`. `entry-date.mapper.ts` now converts validated strings to UTC midnight and serializes database dates through UTC ISO strings; its eight focused unit cases passed. The PostgreSQL integration test verified date-only values round-trip, including leap day and the following day; behavior under multiple process time zones is not separately tested. Do not use local-time date getters. See [PostgreSQL date/time types](https://www.postgresql.org/docs/18/datatype-datetime.html) and [Prisma ORM v7 type mappings](https://www.prisma.io/docs/orm/v7/prisma-client/type-safety/prisma-type-system). The meaning of `isPrivate` is also open; it does not authorize sharing by itself.

Before each schema migration, consider existing data, nullability, foreign keys, unique constraints, cascades, indexes, backfills, and compatibility with deployed code. The first schema defines a non-unique `(userId, entryDate)` index; its generated SQL was reviewed before the initial migration was applied to the development database.

## Boundaries to preserve

The mobile app presents and requests data; the API validates and authorizes it; PostgreSQL persists it. Keep names clear and components, controllers, and services small enough to have one understandable responsibility. Do not scatter API calls through screens, duplicate TanStack Query data in Zustand, put business rules in controllers, or add microservices, Redis, queues, or event infrastructure without a concrete requirement.
