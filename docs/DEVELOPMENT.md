## Prisma development setup

`apps/api/prisma/schema.prisma` defines the first `User` and `DiaryEntry` models. `apps/api/prisma.config.ts` loads the ignored root `.env.local`, which now contains a `DATABASE_URL` using the same local PostgreSQL password as Compose. The Prisma client is generated into `apps/api/src/generated/prisma/`; that directory is ignored by Git and the API's `.prettierignore` so the existing source/test formatting check covers authored code. Keep the URL and password private. Prisma 7 requires explicit client generation after schema changes and on a fresh checkout before application code imports the generated client.

From the repository root, `pnpm --filter api exec prisma validate` checks the schema and configuration without changing the database. `pnpm --filter api exec prisma generate` writes the generated client to the ignored directory without changing the database. Both passed locally with Prisma 7.10.0; `pnpm --filter api exec tsc --noEmit --incremental false`, `pnpm --filter api run lint`, and the API source/test Prettier check also passed. In the agent's restricted PowerShell session, `pnpm.cmd` was used in place of `pnpm` because script execution blocked the `pnpm.ps1` shim. The user's normal PowerShell session may continue using `pnpm`.

An offline `prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script` preview showed two tables, a unique Clerk ID index, a non-unique `(userId, entryDate)` index, and a restrictive foreign key. This preview did not connect to PostgreSQL or create a migration file. A direct `pg` connection then reached `tinta_dev` and confirmed its public schema had no tables. `pnpm --filter api exec prisma migrate dev --create-only --name init_entries` created the initial migration for review, and `pnpm --filter api exec prisma migrate dev` applied it to that empty development database. `pnpm --filter api exec prisma migrate status` reported one migration and an up-to-date schema. The agent could not query Docker service state through its restricted Docker pipe, but direct database connectivity and migration application succeeded. ## Troubleshooting basics

When a workflow fails, capture the exact error, reproduce it, identify recent changes, and test one hypothesis at a time. Check the relevant layer: React Native, Expo or Expo Router, Clerk, the API client or HTTP transport, a NestJS guard, DTO validation, a controller or service, Prisma, PostgreSQL, Docker, environment configuration, CI, or deployment. Check the API address used by a device or emulator, database availability, migration state, and authentication configuration before changing application code. Do not include tokens, credentials, or diary text in shared logs.
