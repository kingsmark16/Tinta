## Test authorship

For each meaningful behavior change with a defined contract, the agent automatically creates or updates the relevant test files. This standing project rule means the user does not need to request a spec each time. The user normally runs the tests and shares the results. Tests should check observable behavior rather than mirror implementation details.

## Test levels

- **Unit tests:** Check focused domain rules, validation, and date handling without network or database dependencies.
- **API HTTP tests:** Start a Nest application in the test process and send requests through its HTTP server. The current suite checks public `GET /` and verifies that protected `GET /auth/me` rejects missing and malformed credentials.
- **API integration tests:** Exercise routes, guards, services, and Prisma against a separate PostgreSQL test database. Run committed migrations there; never point tests at development, staging, or production data.
- **Mobile tests:** The Clerk route-state decision, password authentication helpers, missing-requirements helper, and API request helper have focused specs using Node's built-in test runner. No mobile UI test runner or package script is configured, and CI does not run these specs. The user manually verified account creation, sign-in, and the protected route in Expo. The Home API-check effect uses a latest-callback ref and stable Clerk session dependencies; Prettier and mobile TypeScript checks passed. After the API process was started, the Expo Home showed `API session verified`, manually confirming the live authenticated `/auth/me` response and absence of the render loop. This React effect lifecycle is not covered by an automated component test.
- **End-to-end and manual checks:** Verify the mobile-to-API flow on a device or emulator with synthetic data and separate test accounts.

## Ownership and authentication cases

For each protected user-owned resource, test that:

- User A can perform valid actions on their own resource.
- Missing, invalid, or expired authentication is rejected.
- Invalid input is rejected without storing data.
- User A cannot read, find in a list, change, or delete User B's resource.
- A client-supplied user ID cannot change ownership.

Also cover important domain rules, search/filter/pagination behavior when added, calendar date boundaries, and regressions for fixed bugs. In particular, verify that a diary day remains unchanged across time zones and reject impossible dates. Do not weaken tests merely to make them pass.

## Conventions

- Name tests by behavior and expected result. The API scaffold uses `*.spec.ts` for its unit test and `*.e2e-spec.ts` for its API HTTP test. Follow these conventions unless a clearer one is established.
- Keep test fixtures synthetic. Never include real diary content, live tokens, or secrets in fixtures, screenshots, or CI output.
- Mock external services at meaningful boundaries. Use a real test database for persistence and ownership integration tests rather than mocking Prisma queries that the test is meant to verify.
- Make tests independent and clean up their own data. Keep test accounts and database configuration separate from other environments.

The date unit tests verify the standalone validator. The DTO spec instantiates an equivalent `ValidationPipe` directly; it does not verify that `main.ts` registers the pipe or that an entry route uses the DTO. The auth HTTP suite exercises Clerk middleware in its test app and verifies missing and malformed credentials are rejected. The controller unit spec verifies the success response using mocked Clerk request state. The CORS suite verifies browser preflight from the configured local Expo web origin and rejects an unconfigured origin, but it does not send a valid Clerk session. The mobile helper spec verifies request construction and safe error handling with a synthetic token and stubbed fetch; it does not contact a real API. The helper tests and mobile TypeScript check passed, but a live signed-in request to `/auth/me`, Clerk's production configuration, ownership, persistence, database integration, and date storage across time zones remain unverified. Record new results and unresolved gaps in `PROJECT_STATUS.md`; never describe an unrun or failing check as passed.

The HTTP test constructs an application directly from `AppModule` and does not execute `main.ts`; it mounts Clerk middleware and the CORS policy in the test setup. Before using that harness to test DTO validation, register the same `ValidationPipe` in the test application or move the pipe to an application provider shared by production and tests; otherwise HTTP tests can pass without exercising the production pipe. The passing CORS tests do not prove a valid token can reach `/auth/me` from the running app.
